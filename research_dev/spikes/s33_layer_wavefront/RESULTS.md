# GPU/NPU layer wavefront prototype

Status: implemented and tested on OP15 on 2026-07-21; audit fixes and a fully
captured rerun completed on 2026-07-22.

Scope: this is a fixed mixed-batch scheduling experiment, not a continuous
batching scheduler. It does not admit new arrivals, refill completed rows,
change the prefill/decode mix dynamically, or enforce per-request SLOs.

This prototype runs the first mixed physical ubatch on the GPU. That ubatch
contains a configurable number of decode rows followed by the prefill rows
that fit in the ubatch. At each layer-tile boundary, the GPU copies only the
new prefill KV rows for those layers to the NPU. The NPU starts the remaining
prefill rows at the same time and waits for each tile immediately before it
consumes that tile's KV state.

```text
time ---------------------------------------------------------------------->

GPU mixed U0:  [layers 0..7] [layers 8..15] [layers 16..23] [decode logits]
                         |              |               |
KV tile copy:            v              v               v
NPU prefill:             [layers 0..7]  [layers 8..15]  [layers 16..23] ...
                              ^ dependency for the same layer tile only

CPU control:   START bit, ready-tile counter, abort bit, phase bits
```

The important dependency is layer local. NPU layer tile `k` needs the prefix K
and V generated by GPU tile `k`, but it does not need the GPU to finish later
tiles. Once tile `k` is copied, GPU tile `k + 1` and NPU tile `k` can execute at
the same time.

## Implementation

- `examples/layersplit/hetero-ubatch.cpp` coordinates both contexts through
  graph evaluation callbacks and atomic state.
- `llama_kv_cache_wavefront_reserve()` reserves destination KV positions before
  NPU execution.
- `llama_kv_cache_wavefront_copy()` copies a selected position and layer range
  at a graph boundary.
- `--wavefront-layers 0` selects the previous full-state handoff.
- `--wavefront-layers 1` selects a strict layer-by-layer wavefront.
- The default is an 8-layer tile based on the OP15 measurements below.

The staging API is deliberately narrow. It currently accepts only the ordinary
unified, non-SWA KV cache and the harness restricts wavefront execution to
`general.architecture=qwen2`. Both complete model copies remain resident.

## Verification

Test device and workload:

- Phone: OP15, CPH2749 / OP611FL1, SM8850
- Model: Qwen2.5 0.5B Instruct Q8_0, 24 layers
- Backends: GPUOpenCL for mixed U0, HTP0 for remaining prefill
- Workload: ubatch 32, prompt 128, decode context 16, decode limit 8
- Warmup enabled unless stated otherwise

The original fractional placement audit measured 99.81% of GPU compute nodes
on OpenCL and 99.63% of NPU compute nodes on HTP0. That criterion was too weak
to certify placement. The strict audit added after review rejects every compute
node outside the requested buffer. It reports 18 CPU `GET_ROWS` nodes on the
GPU lane and 8 CPU `GET_ROWS` plus 8 CPU `MUL_MAT` nodes on the NPU lane for
the multi-request workload. Therefore strict placement certification currently
fails with exit code 5. The timing results include these CPU fallbacks and must
not be described as pure GPU-only or NPU-only execution.

The same-backend CPU/CPU test was exact for decode, prefill, and continuation:
relative L2 and maximum absolute logit differences were both zero. The
cross-device GPU/NPU test preserved prefill and continuation argmax values.
Expected backend numeric drift was 0.0355 relative L2 for prefill and 0.0242 for
continuation.

After review, correctness became fail closed. Any argmax mismatch, nonfinite
logit, incomplete continuation, or relative-L2 violation returns exit code 4.
The same-backend relative-L2 limit is `1e-6`; the frozen cross-backend limit is
`0.05`. The transferred prefill is continued for four tokens on both devices.
The first corrected OP15 capture passed all four argmax and numeric checks; its
maximum continuation relative L2 was 0.03936 with no nonfinite values.

## One-decode timing results

Three warmed samples were collected for the two hybrid configurations and for
the all-NPU control using the pre-review harness. Values below are medians in
milliseconds.

| Configuration | Local control | Decode ready | B prefill ready |
| --- | ---: | ---: | ---: |
| All NPU, original mixed batch | 229.119 | 229.119 | 229.119 |
| Legacy GPU U0 then full-state handoff | 283.928 | 71.500 | 246.213 |
| GPU/NPU wavefront, 8-layer tiles | 256.594 | 67.772 | 164.257 |

The local control is the same full mixed batch run on GPU in each hybrid
process. It exposes large run-to-run device-state variation and must be used
when interpreting decode timing.

Raw medians make the 8-layer wavefront appear 5.2% faster than legacy for
decode readiness. Normalized by each run's GPU control, however, the decode
ratio changes from 0.2516 to 0.2642, about 5.0% overhead. Therefore this test
does not establish a decode speedup over the legacy hybrid path.

The robust gain is prefill progress. The normalized B-ready ratio improves by
26.1% compared with the legacy full-state handoff. Against the all-NPU mixed
batch, the wavefront makes decode available 70.4% earlier and finishes B
prefill 28.3% earlier.

For the 8-layer case, per-tile KV transfers totaled about 0.2 to 0.5 ms for
380,928 bytes. Transfer time is not the bottleneck. One-layer tiles exposed
more compute overlap but were slower overall because they introduced 24 graph
boundaries and backend synchronization points. Eight-layer tiles reduce this
to three boundaries.

## Sixteen-decode timing results

The harness was extended with `--decode-requests`. Each decode request has an
independent sequence ID, prompt, seed state, output row, and continuation
token. With `--decode-requests 16 --ubatch 32`, the first physical ubatch is
deterministically:

```text
U0 on GPU: [D0 D1 ... D15] [P0 P1 ... P15]
NPU rest:                     [P16 ... P127]
```

A corrected five-round capture was collected for 16 decode requests and one
128-token prefill request. Every run includes complete JSON, stdout, stderr,
commands, hashes, exit status, and before/after thermal state. The other
parameters were unchanged. Each cell is median `[minimum, maximum]` in
milliseconds.

| Configuration | Decode backend ready | All 16 decode tokens ready | Prefill logits ready |
| --- | ---: | ---: | ---: |
| Original batch, GPU only | 322.3 [319.6, 335.9] | 356.6 [351.8, 418.3] | 329.4 [326.8, 351.9] |
| Original batch, NPU only | 284.9 [278.0, 578.0] | 312.3 [308.2, 659.8] | 291.5 [284.6, 594.7] |
| Legacy GPU U0, full-state handoff | 110.5 [110.1, 111.1] | 190.9 [189.6, 207.4] | 330.9 [329.0, 345.1] |
| GPU/NPU wavefront, 8-layer tiles | 124.4 [113.1, 125.6] | 206.7 [133.3, 211.3] | 238.4 [180.9, 258.1] |

`Decode backend ready` is captured immediately after backend synchronization.
`All 16 decode tokens ready` also includes copying the validation logits and a
serial argmax over 16 vocabularies. Keeping both timestamps prevents this
research-only correctness work from being attributed to accelerator compute.
`Prefill logits ready` is measured on the device that finishes the prefill.

Compared with the NPU-only median, the wavefront makes decode backend output
ready 56.3% earlier, completes all 16 host token checks 33.8% earlier, and
makes prefill logits ready 18.2% earlier. Compared with GPU-only, the latter two
improvements are 42.0% and 27.6%, respectively.

This comparison is stronger than the medians alone: the slowest wavefront
decode-token sample (211.3 ms) is faster than the fastest NPU-only sample
(308.2 ms), and the slowest wavefront prefill sample (258.1 ms) is faster than
the fastest NPU-only sample (284.6 ms).

Compared with the legacy hybrid path, wavefront decode backend readiness is
12.6% slower and all-token readiness is 8.3% slower. In exchange, prefill is
27.9% faster and the completed prefill is available back on GPU 39.2% earlier.
The median layer-tile copy time is 0.37 ms for 196,608 bytes, versus 2.99 ms for
the serialized full-state handoff. Median measured GPU/NPU compute overlap is
25.19 ms.

The NPU-only control is bimodal in this run set: three samples are about 285 to
291 ms and two are about 592 to 595 ms. Battery temperature ranged from 26.3 C
to 27.6 C, and hybrid timings did not show the same 2x split. The table
therefore reports both the median and full range; the source of this HTP
process-level state variation remains unresolved.

All five wavefront and all five legacy runs matched 16 of 16 GPU first-output
argmax values, for 160 first-output checks in total. Each hybrid run also
checked four transferred-prefill continuation steps: all 40 argmax checks and
all 40 relative-L2 checks passed, the maximum relative L2 was 0.03936, and no
nonfinite values were observed. A CPU/CPU oracle was exact for the first decode
outputs, prefill output, and one continuation output. The NPU-only control
consistently differed from the GPU oracle on one decode request
(sequence 12, token 220 instead of 1105), which is backend numeric drift rather
than a scheduling mismatch. The hybrid keeps all decode rows on GPU and avoids
that difference.

The corrected harness still does not compare multi-token decode continuations
against a separate control execution.

## Build and run

```sh
cmake --build build-cpu --target llama-hetero-ubatch -j 8
```

Representative device command:

```sh
./llama-hetero-ubatch \
  -m qwen2.5-0.5b-instruct-q8_0.gguf \
  --dev-gpu GPUOpenCL \
  --dev-npu HTP0 \
  --ubatch 32 \
  --prompt-len 128 \
  --decode-ctx 16 \
  --decode-requests 16 \
  --decode-steps 8 \
  --validation-steps 4 \
  --wavefront-layers 8
```

`reproduce_op15.sh` runs the four configurations in a fixed order and captures
full per-run JSON, stdout, stderr, exit status, commands, binary/model/runtime
hashes, git state, battery temperature, and Android thermal-service snapshots.
Set `REPEATS=5` for the complete protocol.

The exact historical summary lines, run order, commands, hashes, and round-end
battery temperatures are under
`raw/2026-07-21-op15-multi16-recovered/`. Full historical stdout and per-run
thermal snapshots were not retained, and the recovered manifest states this
explicitly. A complete corrected smoke capture is under
`raw/2026-07-22-op15-audit-fix-smoke/`. The fully captured five-round result
set used in the table is under `raw/2026-07-22-op15-audit-fix-r5/`.

Use `--placement-audit` for strict backend-placement evidence. It changes
timing and currently returns exit code 5 because of the CPU compute fallbacks,
so do not combine placement-audit samples with performance samples.
