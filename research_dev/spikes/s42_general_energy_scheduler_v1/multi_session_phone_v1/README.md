# OP15 multi-session resident FFN path

This experiment keeps useful Gemma and Qwen FFN weights resident in three
OP15 FastRPC sessions. It is a physical adapter for the canonical policy in
`research_dev/scheduler`; it does not implement a second scheduler.

## Resident layout

| session | resident slice | measured weight allocation | qualified shape |
| --- | --- | ---: | --- |
| HTP0 | Gemma layers 0-22, GEGLU suffix columns `[9216,15360)` | 3105.05 MiB | decode M=1..16 |
| HTP1 | Qwen layers 0-5, complete SWIGLU FFN `[0,17408)` | 3060.00 MiB | decode M=1 |
| HTP2 | Qwen layers 6-11, complete SWIGLU FFN `[0,17408)` | 3060.00 MiB | decode M=1 |

The measured total is about 9225 MiB of resident weights. Each session stays
below the 3328 MiB FastRPC mapping limit. OP15 has one physical HTP engine, so
these sessions increase residency capacity, not compute parallelism. All
sessions use the same `op15-htp` scheduler resource, and the router serializes
their layer calls. The scheduler plan uses exact allocated bytes, including
the 4 KiB guard page on each HTP weight buffer, rather than the rounded MiB
values shown in the table.

`resident_ffn_session.sh` starts and warms all three workers before publishing
the FunctionFS endpoint. `resident_ffn_router.cpp` accepts a model and shape
arm request, finds disjoint resident shards whose layer masks exactly cover the
request, and routes each layer to its owner. It rejects overlapping shards,
missing layers, model mismatches, and unsupported shapes. The resident workers
survive bounded desktop disconnects; the USB epoch can reconnect without
loading weights again.

For the accepted Qwen route, the server's placement is:

| work | device |
| --- | --- |
| Qwen FFN layers 0-11, decode M=1 | OP15 HTP1 and HTP2 |
| Qwen non-FFN work and FFN layers 12-22 | desktop CPU |
| Qwen last 17 transformer blocks and output | RTX 4060 Ti |
| Qwen prefill | desktop CPU and GPU only |

The scheduler represents HTP1 plus HTP2 as one composite arm. It leases HTP,
FunctionFS, and the desktop USB root once. This route uses
`execution_mode="full_replacement"`: the phone replaces the entire FFN for
the selected layers, so admission uses end-to-end latency and fleet energy.
The exposed join-wait gate remains applicable to partial parallel splits.

## Memory and identity gates

The checked-in residency plan is generated by
`build_op15_residency_plan.py`. It binds the full model SHA-256, exact layer and
column manifest, worker-reported weight digest, mapping limit, physical M
range, phone serial, and shared resources. The phone must publish matching
WARM receipts and at least 2 GiB `MemAvailable` before an arm can pass.
Each scheduler `weight_hash` is SHA-256 over that canonical slice manifest;
the manifest includes the full model SHA-256 and the worker's physical weight
digest.

`plan_unified_qwen_screen.py` imports only the public
`research_dev.scheduler` API. Given the repeated physical evidence and the
resident plan, it selects `qwen-full-ffn-layers-0-11-m1`, emits a composite
HTP1 plus HTP2 arm, and leases HTP, FunctionFS, and USB as one phone path. Its
hash-bound output is checked in under `results/`.

The physical runs left 2,315,308 to 2,493,896 KiB available after all sessions
were warm. This is a narrow margin. Adding another slice or qualifying larger
M values requires a new memory and energy measurement.

## Reproduction

Build the host and Android probes with:

```sh
./build.sh
```

Run one physical arm on the desktop that owns OP15:

```sh
./run_qwen_full_energy_arm.sh control 1 /absolute/results/control-r1 5037
./run_qwen_full_energy_arm.sh op15 1 /absolute/results/op15-r1 5037
```

Use an ABBA order for two repeats. The control starts the identical resident
phone layout and includes its idle energy, but executes zero phone FFN calls.
Both arms warm the server once before the paid interval. Validate the four
runs with `analyze_qwen_full_energy_pair.py`.

See `RESULTS.md` for the measured outcome and limitations.
